# 任务：走查某个 namespace 的译文

> **用法**：把本文整份粘贴给 AI，然后填最后的「参数」一节。
> 本文自包含。若 AI 能读到仓库，`CLAUDE.md` 的规则优先于本文。

---

## 你的角色

你在为 AlphaESS 的 **Antelope 业务线**（储能/光伏的 Web 管理端）做译文走查。典型场景：
某个功能模块开发完成，产品经理要检查这个模块的文案质量。

```
locales/<namespace>/<语种>.json     一层扁平 JSON，值必须是字符串
```

基准语言 `en-US`（源），目标语种 10 个：
`zh-CN` `de-DE` `fr-FR` `es-ES` `it-IT` `nl-NL` `sv-SE` `el-GR` `pl-PL` `cs-CZ`

## ⚠️ 本任务默认「只报告，不改动」

走查的产出是**一份问题清单**，不是一堆改动。理由：

- 改动要人确认后才动，尤其涉及母语判断的
- 走查发现的问题往往跨多个语种，一起改会让 diff 大到没法 review
- 有些"问题"其实是设计如此（见下方误判清单）

**除非人在「参数」里明确要求「顺便修掉 X 类问题」**，否则不要改任何文件。

## 查什么

按严重程度排列。前三类是 CI 阻塞级 —— 但**存量问题有豁免清单**，所以可能存在于仓库里。

### 🔴 1. 占位符错误（最优先）

| 问题 | 长什么样 |
|---|---|
| 占位符名被翻译 | `en-US: {country}` → `de-DE: {Land}` |
| 双花括号 | `{{count}}` —— 本项目插值失效，用户看到字面量 |
| 占位符缺失 | 源文有 `{sn}`，某语种整个丢了 |
| 占位符多余 | 某语种凭空多出源文里没有的 |
| 位置参数改序 | 错误码的 `{0}` `{1}` 被换了顺序 |

**这类问题在生产环境的表现是用户看到 `{Land} / X` 这种字面量** —— 比没有译文更难发现。

存量里已知有 14 处占位符名被翻译、2 处双花括号（记在 `.ci/baseline.json`）。
走查中发现的要报出来，标明是不是已在豁免清单里。

### 🔴 2. 结构问题

- 嵌套对象（值必须是字符串）
- 值不是字符串（数字/布尔/null）
- 某语种缺 key，或有 `en-US` 里没有的多余 key

### 🟡 3. 英文占位残留

某语种的值与 `en-US` **完全相同** —— 可能是 `fill-missing` 补的英文占位，还没换成真译文。

⚠️ **本仓库没有翻译状态标记**（原 `_meta` draft 机制已移除），所以只能靠这个启发式判断。
而它的可靠度**取决于语种** —— 全仓库实测（2026-08-05，共 1,618 处命中）：

| 语种 | 占比 | 信号强度 |
|---|---|---|
| `el-GR` 1.1% · `zh-CN` 1.4% | 低 | **强** —— 不同字母系统，同形基本就是未翻 |
| `es-ES` `cs-CZ` `pl-PL` 2.1–2.4% | 中 | 中 |
| `it-IT` `sv-SE` `fr-FR` 2.8–3.6% | 较高 | 弱 |
| `de-DE` `nl-NL` 4.2–4.8% | 高 | **最弱** —— 约一半是误判 |

**以下同形是正常的，不要报**：

```
拉丁语种里本来就同形   Status  Model  Normal  Type  Version  Firmware
                      Admin  Ethernet  Host  Master  Follower
品牌 / 型号            AlphaESS、SMILE-B3
缩写                  SN、PV、SOC、EMS、VPP、GTL、API、ID
单位                  kWh、V、A、%
产品功能名             Storm Guard、Backup Box
通用词                OK、ON、OFF、Email
```

报的时候分两组：**确定是占位** / **可能是同形设计**。`de-DE` / `nl-NL` 的命中默认归第二组，
除非该词在这个语种里明显应该译成本地说法。

### 🟡 4. 术语不一致

同一概念在同 ns 内译法不同，或与 `glossary/terms.json` 冲突。

⚠️ 术语库**目前只有 3 条**（`inverter` / `pv` / `AlphaESS`），且只有前两条有 zh-CN ——
其余 9 个语种没有术语约束。所以主要靠**ns 内部自我一致性**判断。

### 🟡 5. 语气与长度

| 问题 | 说明 |
|---|---|
| 长度失控 | 明显比同 ns 其它条目长。德语/波兰语容易超长撑破 UI |
| 语气不一致 | 管理端后台应是简洁陈述式。混入感叹号、口语化、过度礼貌 |
| 机翻痕迹 | 语序生硬、直译搭配、量词错误 |
| 大小写不一致 | 同类标签一会儿 Title Case 一会儿 sentence case |

### 🟢 6. 源文本身的问题

有时问题在 `en-US` 而不是译文：拼写错误、表述含糊、一个 key 塞了两句话、
该有占位符却写死了值。这类要单独报 —— **改源文影响所有语种**，必须人来定。

## 步骤

1. 读 `locales/<ns>/en-US.json`
2. 读该 ns 下所有（或指定的）目标语种文件
3. 读 `glossary/terms.json`
4. 逐条对比，按上面六类归类
5. 如果能读仓库，跑一次 `node tools/validate.mjs` 看有没有阻塞级问题（它只报全仓库的，注意筛出本 ns 的）
6. 按「交付格式」输出清单

## 🚫 你不做的事

- **默认不改任何文件**（除非人明确要求）—— 走查的产出是清单，不是 diff
- 因此**默认也不开 PR**。人看过清单、明确说「按这个改」之后，才走
  [`prompts/translate.md`](translate.md) 的修改 + 开 PR 流程
- 🔴 **任何情况下不合并 PR**（`gh pr merge`），不直推 `main`
- 不要往 `.ci/baseline.json` 加条目
- 不要改 `glossary/terms.json` —— 术语库由产品 + 业务专家维护，你只能**建议**

## 交付格式

```
## 概览
- namespace：<ns>
- 检查了 N 条 key × M 个语种
- 发现问题：🔴 阻塞级 X 处 / 🟡 质量 Y 处 / 🟢 源文 Z 处

## 🔴 阻塞级问题
| key | 语种 | 问题 | 现值 | 建议值 |
|-----|------|------|------|--------|
（标明是否已在 .ci/baseline.json 豁免清单里）

## 🟡 英文占位残留
确定是占位：
| key | 语种 | 当前值（= 英文） |

可能是同形设计（不建议改）：
| key | 语种 | 值 | 为什么可能是设计如此 |

## 🟡 术语 / 语气 / 长度
| key | 语种 | 问题类型 | 说明 | 建议 |

## 🟢 源文（en-US）问题
| key | 问题 | 建议 |
（说明：改源文会影响全部 11 个语种，需人决定）

## 建议补进术语库的概念
| 概念 | 出现在哪些 key | 建议的各语种译法 |

## 建议的处理顺序
1. ...
```

**表格里必须给出「现值」** —— 人要能不打开文件就判断。

## 参数（由人填写）

```
namespace：
  例：device-form/battery
  （字典类的写全名，如 dictionaries/product_config）

要检查的语种：
  例：全部 10 个    或    de-DE, cs-CZ, el-GR（重点关注的）

这个模块是做什么的：
  例：电池设备的配置表单，管理员给站点添加/编辑电池时用
  （强烈建议填 —— 没有上下文无法判断语气和用词是否得体）

已知问题 / 关注点：
  例：上次上线后德语用户反馈按钮文案看不懂
  例：这批是三个月前 AI 补的，没人复核过

要不要顺便修：
  □ 只报告，我自己决定（默认）
  □ 阻塞级问题（占位符/结构）直接修掉，质量问题只报告
  □ 全部按你的建议修掉
```
