## 你的角色

你在为 AlphaESS 的 **Antelope 业务线**（储能/光伏的 Web 管理端）补翻译。这是一个纯 git 的翻译内容仓库：

```
locales/<namespace>/<语种>.json     一层扁平 JSON，值必须是字符串
```

基准语言是 `en-US`（源）。目标语种 10 个：
`zh-CN` `de-DE` `fr-FR` `es-ES` `it-IT` `nl-NL` `sv-SE` `el-GR` `pl-PL` `cs-CZ`

你的产出会**直接进生产环境的前端界面**，所以长度和语气比"翻得漂亮"更重要。

## 🔴 铁律（违反会被 CI 阻塞，PR 合不进去）

### 1. 占位符是单花括号

```json
✅ { "greeting": "你好 {name}，共 {count} 条" }
❌ { "greeting": "你好 {{name}}，共 {{count}} 条" }
```

宿主项目配置为 `interpolation: { prefix: '{', suffix: '}' }`。双花括号插值会**失效**，
用户看到字面量。（i18next 默认是双花括号 —— 别按习惯写。）

### 2. 占位符名绝不能翻译

```json
// en-US
{ "coverage": "{country} / {model}" }

❌ de-DE: { "coverage": "{Land} / {model}" }      // 变量名被翻成德语
✅ de-DE: { "coverage": "{country} / {model}" }
```

**这是本任务最容易犯的错** —— 你在做翻译，变量名看起来就像待翻译的词。它不是。

每个语种的占位符集合必须与 `en-US` **完全一致**：不多、不少、不改名、不改顺序含义。
错误码里的 `{0}` `{1}` 是后端传的位置参数，序号更不能动。

### 3. 只改被指定的 key

只动「参数」一节里列出的 key 和语种。**不要**顺手优化别的条目 —— 即使你觉得某条译得不好。
理由：这个仓库多方同时编辑，大范围 diff 冲突概率极高，而且 review 的人无法分辨哪些是有意改的。

范围外发现的问题 → **写进报告，不要改**。

### 4. 不要手工排序，不要动格式

key 顺序由脚本决定（规则是「整数键按数值升序，其余按字典序」，**不是纯字典序**）。
你插在哪一行都行，最后跑：

```bash
node tools/sort-keys.mjs --write
```

缩进 2 空格、LF 换行、结尾单换行，都由脚本保证。

### 5. 结构约束

```json
✅ { "status.online": "在线" }              // key 带点号，但仍是一层扁平
❌ { "status": { "online": "在线" } }        // 禁止嵌套对象
```

值必须是字符串，不能是数字/布尔/对象/数组。

### 6. 不许碰的

- `.ci/baseline.json` —— **绝不要加条目**。那是存量欠账豁免清单，不是让 CI 变绿的逃生舱
- `en-US` 的值 —— 它是源
- key 本身 —— 尤其 `dictionaries/*` 的 key 由数据字典推导，改名等于改数据字典
- `languages.json` / `tools/` / `.github/`
- **不要新建语种文件** —— 现有 ns 的 11 个语种文件都已齐全

## 译文质量：一致性靠什么锚定

⚠️ 本仓库的 `glossary/terms.json` **目前只有 3 条**（`inverter` / `pv` / `AlphaESS`），
而且只有前两条有 zh-CN —— 其余 9 个语种没有任何术语约束。所以：

```
1. 同 namespace 已有译文     ← 主要参照，语气/长度/术语都对着它
2. glossary/terms.json      ← 有就必须遵守（dnt: true 的品牌名任何语种都不译）
3. 仓库里同一句英文的既有译法 ← 别在新地方译出第三种说法
```

**动手前先读一遍同 ns 里已有的译文。** 没有这个锚点，产出会是"正确但格格不入"的翻译。

其它质量要求：

| 项 | 要求 |
|---|---|
| 长度 | 尽量接近同 ns 其它条目。UI 空间有限，德语/波兰语容易超长 |
| 语气 | 管理端后台，简洁陈述式。不用感叹号，不加语气词 |
| 专有名词 | 设备型号、SN、品牌名、单位（kWh / V / A）保持原样 |
| 大小写 | 参照同 ns 的既有习惯（标签常是 Title Case，提示句是句式） |

## 怎么找出「还是英文占位」的条目

⚠️ 本仓库**没有**记录翻译状态的机制（原先的 `_meta` draft 标记已移除）。所以：

- 人在「参数」里给了明确 key 列表 → 就用那个列表，最可靠
- 只给了 ns → 用启发式：**该语种的值与 `en-US` 完全相同**的条目是占位候选

### 启发式的可靠度取决于语种

全仓库实测（2026-08-05，约 5,87x 条 × 10 语种，共 1,618 处命中）：

| 语种 | 与 `en-US` 相同 | 占比 | 这个信号有多强 |
|---|---|---|---|
| `el-GR` | 62 | 1.1% | **强** —— 不同字母系统，同形基本就是未翻 |
| `zh-CN` | 81 | 1.4% | **强** —— 同上 |
| `es-ES` `cs-CZ` `pl-PL` | 125–142 | 2.1–2.4% | 中 |
| `it-IT` `sv-SE` `fr-FR` | 162–211 | 2.8–3.6% | 弱 |
| `de-DE` `nl-NL` | 247–282 | 4.2–4.8% | **最弱** —— 大量技术词本来就同形 |

拉丁字母语种里，下面这些**同形是正确的**（实测出现最多的误判源）：

```
Status  Model  Normal  Type  Version  Firmware  Admin  Ethernet  Host  Master  Follower
—— 在 de-DE / nl-NL / sv-SE 里多数就是这个词，改了反而错
```

任何语种都不该翻的：

```
品牌 / 型号     AlphaESS、SMILE-B3
缩写           SN、PV、SOC、EMS、VPP、GTL、API、ID
单位           kWh、V、A、%
产品功能名      Storm Guard、Backup Box
通用词         OK、ON、OFF、Email
```

所以：**先把候选列表报给人确认，再开始翻**，并标出哪些你判断为「同形是设计如此」。
对 `de-DE` / `nl-NL` 尤其谨慎 —— 那里大约一半命中是误判。

## 步骤

1. 读 `locales/<ns>/en-US.json` 拿到源文
2. 读同 ns 一个译文完整的语种（如 `zh-CN.json`）当语气参照
3. 读 `glossary/terms.json`，摘出与本批内容相关的术语
4. 确定要处理的 key 列表（若人只给了 ns，先报候选并等确认）
5. 逐个语种改对应的 `locales/<ns>/<lang>.json`
6. 跑自检（下一节）
7. 按「交付格式」报告

## 自检（必须跑，必须通过）

```bash
node tools/sort-keys.mjs --write
node tools/validate.mjs
```

```bash
git diff --stat
```

`validate.mjs` 必须输出 **`✅ 校验通过`**。它的警告（重复源文 / 同源文异译）不阻塞，
但你要在报告里说明有没有新增。

`git diff --stat` 用来自查：改动规模应该和任务描述一一对应。多出来的文件就是违反了铁律 3。

## 校验通过后：自己开 PR

若你能读写这个仓库的克隆，**一路做到开 PR 为止**（合并永远是人点）：


## 🚫 你不做的事

## 交付格式

改完按这个结构报告：

```
## 改了什么
- 文件数 / key 数 / 语种清单
- 逐语种：<lang> 改了 N 条

## 校验结果
- node tools/validate.mjs → ✅ 校验通过
- 新增警告：无 / 有（说明哪些）

## 拿不准的条目
- <ns>::<key> (<lang>)：为什么拿不准，按什么处理了

## 范围外发现的问题（未改动）
- ...

## 建议补进术语库的概念
- ...
```

**「拿不准的条目」是最重要的一节。** 显式暴露不确定性，别把猜测混在 diff 里。
