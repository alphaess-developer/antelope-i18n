# 错误码文案

本目录存放后端错误码对应的用户提示文案。

## key 就是错误码

```json
{
  "6028": "{0} 不能为空",
  "6032": "{0} 已存在"
}
```

key 是后端返回的 `code` 字段（字符串形式的数字）。前端在 `useFetch` 里按 `tE(apiError.code.toString())` 查询。

## 三个特殊 key

| key | 用途 |
|---|---|
| `0000` | **通用兜底**。任何错误码查不到文案时显示这条，带 `{errorCode}` 占位符让用户能看到原始码 |
| `99999` | 约定为「后端直接返回文案」，前端**不查翻译**，直接用响应里的 `error` 字段 |
| `Username cannot be changed` | 历史遗留的非数字 key，勿新增同类 |

## ⚠️ 占位符 = 后端字段名

错误码文案的插值参数来自后端响应的 `data` 对象，**占位符名必须与后端的字段名完全一致**：

```
后端返回 { code: 6032, data: { 0: "SN12345" } }
文案       "{0} 已存在"
渲染       "SN12345 已存在"
```

所以：

- `{0}` `{1}` 是**位置参数**，后端按顺序传，不能改序号
- 具名占位符（如 `{sn}`）必须与后端字段名一字不差
- **绝对不要翻译占位符名** —— 各语种必须完全一致

写错占位符名的后果是显示成字面量（用户看到 `{Nummer} 已存在`），比缺文案更难发现。CI 有阻塞级检查拦这个。

## 新增 / 修正错误码：完整步骤

> 后端同事的极简版说明见 **[docs/backend-guide.md](../../../docs/backend-guide.md)**，可直接转发给后端团队。

### 新增一条

**只需要改 `en-US.json`。** 其余 10 个语种会被 CI 自动补齐。

```
1. 打开 en-US.json，按 . 键进入浏览器版 VS Code
2. 加一条：  "6199": "Device {sn} is offline"
   顺序不用纠结 —— CI 会自动按数值排序
3. 提交 → 自动开 PR
4. fill-missing workflow 用英文占位补齐其余语种（几十秒）
5. CI 全绿 → 合并
6. 后续 PM/AI 把占位英文优化成真译文（_meta 里有待办清单）
```

为什么用英文占位而不是留空：宿主项目配置了 `fallbackLng: false`，缺 key 会**直接把 key 名显示给用户**。显示英文远好于显示 `some_key_name`。

### 修正一条已有的

直接改对应语种的文件即可。注意：

- 改 `en-US`（基准语言）**不会**自动同步到其他语种 —— 其他语种的旧译文仍在，需要一并检查
- 若基准语言改动导致语义变化，建议把其余语种也一并改，或在 PR 里说明留给 PM 处理

### 批量补齐 / 优化

```bash
node tools/fill-missing.mjs              # 看有哪些缺
node tools/fill-missing.mjs --write      # 用基准语言占位补齐
node tools/fill-missing.mjs --write --ns=dictionaries/error-code   # 只处理本 ns
```

补齐后记得从 `.ci/baseline.json` 的 `missingKeys` 里删掉已解决的条目。

## ⏱ 时效与逃生舱

本仓库的译文在 `antelope-web` **构建时**打进产物，所以新增错误码要等**前端发版**才生效。

**急用**：让接口返回 `code: 99999` + `error` 字段直接带文案（见上表的特殊 key），前端会原样显示，不必等发版。下次前端发版后再切正式错误码。

中间窗口不会出事 —— 前端有三层兜底，最差情况是显示 `0000` 的通用提示 + 错误码数字，**不会白屏、不会显示裸 key**。

## 为什么不挪到独立的顶层目录

评估过两个方案，都不如现状：

| 方案 | 问题 |
|---|---|
| 上移到 `locales/error-codes/` | `locales/` 下有约 40 个同级目录，从「dictionaries 的子目录」变成「40 个之一」，**并没有更好找** |
| 与 `locales/` 平级独立一层 | 会留下四处永久特例：glob 要加第二个模式、`listNamespaces()` 要扫两个根、CI 校验同上，**而 i18n Ally 的 `pathMatcher` 是单值配置，会让编辑器插件对错误码失效** —— 那正是这套方案要解决的核心痛点 |

**可发现性不该靠目录深度解决。** 实际起作用的是三样东西，它们都与路径无关：

1. **直达链接** —— 给后端同事一个书签，而不是让他们浏览目录
2. **CODEOWNERS** —— 改这个目录自动 request 后端 + 前端双 review
3. **自动补齐语种** —— 消除「要填 11 个语种」这个真正的摩擦点

顺带：维持现路径意味着 `antelope-web` 侧**零代码改动**（`useFetch.tsx` 和 `i18n/index.ts` 的 ns 名不用动）。
